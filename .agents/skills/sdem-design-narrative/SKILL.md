# A design narrative from the workspace

SDEM's `sdem document` is the **structured reference** of a layer: every record, attribute and link, generated by rules. It never writes prose. **You write the prose** — and SDEM checks it. The narrative is a document for people, **never architecture data**: you do not change the workspace while writing it.

## 1. Get the facts — only from SDEM

```bash
sdem document --workspace <dir> --layer A3 --json       # one layer; --layer all for every layer
```

Read the JSON: `sections` (records by type: description, attributes, `links_out`/`links_in` inside the layer, `connections` to other layers with `status`, `mapping_id` and evidence, `provenance`), `requirements`, and `gaps`. **That JSON is your only source.** Not your knowledge of banking, not the record names' usual meaning, not a document you read earlier — if the JSON does not say it, the narrative does not say it.

Ask the architect who reads it (an executive overview, a reviewer, a new team member) and how long it should be. Default: one page per layer.

## 2. Write it — every fact cited

- **Cite every record you mention, every time, in the same paragraph:** `Payments Hub [APP-PAY-HUB]`.
- **Cite every link you state:**
  - inside a layer — `[SOURCE kind TARGET]` with the kind from `links_out`, e.g. `[APP-PAY-HUB composition CMP-PAY-CAPTURE]`;
  - between layers — the connection's link id, e.g. `[PAY-108]`, or `[SOURCE RELATIONSHIP TARGET]`, e.g. `[APP-PAY-HUB DEPLOYED_ON INF-K8S-PAY-PROD]`.
  Only **approved** connections are facts. A proposed one, if you mention it at all, is said to be *proposed*.
- **Inferred records** (`provenance` says *inferred — not yet confirmed*) are said to be inferred in the same paragraph: "AID inferred Ledger Core [APP-LEDGER-CORE]; an architect has not yet confirmed it."
- **Attribute values** are quoted as the JSON gives them ("recovery time objective 2h"), never rounded, translated or explained beyond what the record says.
- **End with the gaps:** a section *Gaps and open items* from the JSON's `gaps` — what is unconfirmed, unconnected, unknown. Never fill a gap with a likely answer.
- **Your own view** (a risk you notice, a suggestion) goes in a separate section headed *Suggestions (not from the workspace)*, with no citations, so no reader mistakes it for a fact.
- Plain words; the architect's names for things; no marketing.

Save it outside the layer files, e.g. `<dir>/narratives/a3-narrative.md` or `work/a3-narrative.md`.

## 3. Check it — until it has no errors

```bash
sdem document verify work/a3-narrative.md --workspace <dir> --json
```

| Finding | What it means | What you do |
|---|---|---|
| `unknown_id` (error) | a cited id is not in the workspace | you invented or mistyped it: fix the id, or remove the sentence |
| `unknown_link` (error) | a stated link is not in the workspace | remove the claim — never add the link to make the check pass |
| `not_approved` (error) | the connection is proposed, not approved | say *proposed*, or leave it out |
| `no_citations` (error) | nothing is cited | rewrite with citations |
| `uncited_name` (warning) | a record is named without its id | add the id |
| `unconfirmed_as_fact` (warning) | an inferred record is stated as fact | say it is inferred and not yet confirmed |
| `gaps_not_mentioned` (warning) | the workspace has open items the text leaves out | add the *Gaps and open items* section |

Run it again until there are **no errors**; clear the warnings unless the architect agrees otherwise. Passing the check means every citation is real — **not** that every sentence is right: the check cannot read your wording.

## 4. Hand it over

Tell the architect: which command the facts came from, that `sdem document verify` passed (with any warnings left and why), and the *Suggestions* you made. **The architect reads it before it is shared.** If the narrative showed something wrong in the design, the fix is a change set (skill `sdem-change-sets`) — never an edit to the narrative to hide it. End with `sdem handback --workspace <dir> --json`.
