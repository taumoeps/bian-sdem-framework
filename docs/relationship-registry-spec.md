# SDEM Architecture Relationship Registry Specification

Generated by `python -m sdem.spec` from `schema/relationship-registry.schema.json`, the lifecycle in `sdem/diff.py` and the relationship type catalogue (`schema/relationship-types.json`); the test suite checks it is current. Overview: `docs/sdem-overview.md`.

The **Architecture Relationship Registry** holds the actual relationships between real architecture entities across levels: each with evidence, confidence, status, version and approval provenance. It is built by the Architecture Relationship Inference Engine (records `proposed`) and governed by architects; the graph loader reads its `approved` records into the federated architecture knowledge graph. In this repository a registry is one JSON file per estate, `examples/<estate>/mappings.json`.

## 1. Document

| Field | Required | Meaning |
|---|---|---|
| `registry_version` | no | version of the **relationship type catalogue** the records were written against (legacy name) |
| `metamodel_version` | no | version of the Architecture Metamodel |
| `mappings` | yes | the list of relationship records (legacy name) |

## 2. Relationship record

| Field | Type | Required | Meaning |
|---|---|---|---|
| `mapping_id` | string | yes | the record's permanent ID (legacy name) |
| `source` | entity | yes | the entity the relationship starts from (§3) |
| `target` | entity | yes | the entity it points to (§3) |
| `relationship` | string | yes | one of the nine catalogued types (§5); adjacent levels only |
| `perspective` | process, information, architecture | no | architecture, process or information |
| `status` | proposed, validated, needs_review, approved, rejected, superseded | yes | lifecycle state (§4) |
| `evidence` | array | yes | `kind:reference` items; the kinds must include the type's required evidence (§5) |
| `rationale` | string | yes | why the relationship holds: the working |
| `baseline_id` | string | yes | the release the record belongs to |
| `confidence` | number | no | 0–1, the rule's band |
| `bian_release` | string | no | required on BIAN-authority types before approval (a proposed or needs_review link may wait for it — F-1) |
| `reviewer_id` | string | no | the approving architect |
| `created_by` | string | no | who or what proposed it (engine, rule, architect) |
| `approved_at` | string | no | approval date |
| `valid_from` | string | no | start of validity |
| `valid_to` | string | no | end of validity; set on supersession |
| `previous_mapping_id` | string | no | the record this one supersedes (legacy name) |

## 3. Entity reference (source, target)

| Field | Required |
|---|---|
| `id` | yes |
| `type` | yes |
| `version` | yes |
| `canonical_id` | no |
| `source_system` | no |
| `source_entity_id` | no |

An end must resolve to an instance in the local architecture knowledge graph its type prefix names, with that id and version, whose type is the referenced type or a descendant of it.

## 4. Lifecycle

| From | May become |
|---|---|
| `proposed` | `approved`, `needs_review`, `rejected`, `validated` |
| `validated` | `approved`, `needs_review`, `rejected` |
| `needs_review` | `approved`, `proposed`, `rejected`, `validated` |
| `approved` | `superseded` |
| `rejected` | — (final) |
| `superseded` | — (final) |

**Immutability.** A record in `approved`, `rejected`, `superseded` is frozen: no field may change, except that an `approved` record may become `superseded`, changing only `status`, `valid_to`. A change is a **new record** whose `previous_mapping_id` names the old one. Records are never deleted. `sdem-diff` enforces this against the previous version.

## 5. Relationship types and required evidence

From the relationship type catalogue (Architecture Metamodel).

| Type | Source → target | Authority | Required evidence |
|---|---|---|---|
| `SUPPORTED_BY` (CAPABILITY_SUPPORTED_BY_DOMAIN) | A1.BusinessCapability → A2.ServiceDomain | bian_alignment_guidance | business_architecture_document, domain_scope_assessment |
| `ALIGNED_TO` (VALUE_STREAM_ALIGNED_TO_SCENARIO) | A1.ValueStream → A2.BusinessScenario | bian_alignment_guidance | process_model, scenario_suitability_review |
| `USES_DOMAIN` (PROCESS_USES_DOMAIN) | A1.BusinessProcess → A2.ServiceDomain | enterprise_rule | process_model |
| `ALIGNED_TO` (BUSINESS_OBJECT_ALIGNED_TO_BIAN_OBJECT) | A1.BusinessObject → A2.BusinessObject | bian_alignment_guidance | business_glossary, object_alignment_review |
| `REALIZED_BY` (DOMAIN_REALIZED_BY_COMPONENT) | A2.ServiceDomain → A3.ApplicationComponent | enterprise_rule | application_architecture_document |
| `IMPLEMENTED_BY` (OPERATION_IMPLEMENTED_BY_API) | A2.ServiceOperation → A3.APIOperation | enterprise_rule | api_contract |
| `MAPPED_TO` (BIAN_OBJECT_MAPPED_TO_DATA_ENTITY) | A2.BusinessObject → A3.DataEntity | enterprise_rule | data_model |
| `DEPLOYED_ON` (COMPONENT_DEPLOYED_ON_INFRASTRUCTURE) | A3.ApplicationComponent → A4.InfrastructureComponent | enterprise_rule | deployment_design |
| `DEPLOYED_AS` (COMPONENT_DEPLOYED_AS_DEPLOYMENT) | A3.ApplicationComponent → A4.Deployment | enterprise_rule | deployment_design |

## 6. Validation

| Check | Tool |
|---|---|
| record shape, catalogued type, adjacency, evidence kinds, BIAN fields | `sdem-validate` |
| both ends resolve in the local knowledge graphs | `sdem-graph check` |
| no edits to frozen records; only permitted transitions | `sdem-diff` |

## 7. Legacy names

The relationship type catalogue keeps the field names `mappings`, `mapping_id` and `previous_mapping_id`, and the catalogue keeps `mapping_type_id` and `registry_version`, because they sit inside immutable approved records. Renaming them would need a versioned migration (a reader accepting both names and a converter), with approved history preserved by supersession. The previous schema path `schema/mapping.schema.json` is kept as a deprecated copy for v0.7.
