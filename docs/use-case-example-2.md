# Use-case example 2 — testing Architecture Inference Design (AID)

> **Status: AID built and run 2026-10-27 — expected results sealed before any run (commit 17dbd33); the baseline is kept at the end.**

## Key words

- **AID** — Architecture Inference Design: projects the architecture layers you don't have, from the ones you do.
- **Projected design** — what AID produces: inferred, not real, with a confidence on every element.
- **Gap analysis** — comparing the projected design with the real one.
- **BIAN catalogue** — the list of BIAN service domains AID chooses from.

## Goal

Measure how close AID's projected design is to the real design.

## Method

1. Take an estate where all four layers are known: **payment-initiation**.
2. **Hide** some layers.
3. Let AID **project** them.
4. **Compare** with the hidden real layers.

**BIAN catalogue for the test:** the BIAN layer (A2) of all 7 example estates combined, so AID must *choose* the right service domains from several — not be handed the answer.

## Five runs

| Run | Architect has | AID projects | Real use |
|---|---|---|---|
| 1 | A1 + A2 | A3, A4 | "I've chosen my BIAN domains — what applications and deployments follow?" |
| 2 | A1 only | A2, A3, A4 | "I only have business design — preview everything below" |
| 3 | A4 only | A3, A2, A1 | "I only have infrastructure — what does it support?" |
| 4 | A3 + A4 | A2, A1 | "I have applications and technology — what business do they serve?" |
| 5 | A1 + A3 | A2 | "I have business and applications — fill in the BIAN layer between" |

## What we measure

For each run and layer: ✅ **matched** · ➕ **projected only** · ➖ **real only** · ≠ **differs** — giving precision and recall.

And the safety controls:

- **CTL-16** — a projection put into real data, or approved, is rejected.
- **CTL-17** — every projected element has its provenance; none is above medium confidence; no BIAN element is invented.

## Expected results (sealed)

| Run | Expected |
|---|---|
| 1 | every service domain gets a projected component, and every operation with a REST form an API; **no platform, environment or network invented**; APIs match the real method and path for **at least 2 of 6** (today's level), higher after the qualifier fix (AID-Q04) |
| 2 | **all** real service domains found where the business names its operations; few wrong |
| 3 | **every** application the technology names is projected; BIAN domains suggested at low confidence; the business layer the weakest |
| 4 | BIAN domains correct where the APIs carry BIAN-style operations |
| 5 | at least as accurate as run 2, because both sides agree |
| Safety | CTL-16 and CTL-17 hold **100%** — no exceptions |

## Starting point — honest

Only **run 1** works today (the engine's design mode). Runs 2–5 and the safety controls need AID built. So:

1. **Baseline now:** run 1 gives real numbers; runs 2–5 report *not built*.
2. **Build AID, then re-run** — each re-run shows measured progress against these sealed expectations.

## Output

Per run: a gap-analysis table (element, projected, real, result, confidence), precision and recall per layer, and the safety-control results — with evidence files, as in example 1.

## Limits

Made-up data · a small BIAN catalogue (7 estates), not the full licensed BIAN · AID's rules are tuned on SDEM's own examples, so a test written by someone else is still needed.

## Results — run 2026-10-27 (AID built)

**Verdict:** 12 of 12 sealed expectations met across the five runs; safety controls 15 of 15 tests pass — every projection stayed apart, marked and capped.

Generated by `python scripts/use_case_example_2.py` with `sdem/aid.py`; evidence in [`evidence/use-case-example-2/`](evidence/use-case-example-2/manifest.json) (one projection package and one gap analysis per run). The baseline before AID was built is kept at the end for comparison.

**How to read the tables.** *Layers (from → to)* / *Projected (from → to)* shows the direction AID projected in — e.g. **A1 → A2** means inferred from the business layer into the BIAN layer. *Link stored as* shows the link the way the rulebook stores it, which can point the other way: AID projecting upwards **A3 → A2** still stores `REALIZED_BY` as A2 → A3. Every record is tagged with its layer and where it comes from: **real** (a layer the architect has), **projected** (made by AID in this run) or **BIAN catalogue**. Every projected element shows: the **source** — the real records it was inferred from; the **rule** and its **published source** (see *Sources* at the end); the **reasoning**; the **confidence** (0.6 = medium, 0.4 = low — AID never goes higher); and the **result** against the hidden real design: ✅ matched · ≠ differs · ➕ projected only · ➖ real only (missed).

### Run 1 — has A1 + A2, projects A3, A4

**The architect has** the business layer (A1) — 16 records (4 ValueStreamStage, 4 BusinessActivity, 2 BusinessCapability, 2 BusinessProcess) and the BIAN layer (A2) — 24 records (6 ServiceOperation, 3 ServiceDomain, 3 AssetType, 2 FunctionalPattern). Everything else is hidden from AID.

**Projection path:** **A2 → A3** (6 elements) · **A3 → A4** (1 element)

**What AID did, step by step:**

1. **F2** (A2 → A3) — applied BIAN's container pattern: one application component per service domain, one API per service operation (BIAN REST mapping).
2. **F3** (A3 → A4) — projected one deployment per component — and, by rule, no platform, environment or network.

**What it projected:** 6 records in the application layer (A3), 1 record in the technology layer (A4), and 7 links. Of these, 7 are the main design elements (domains, components, APIs, deployments, capabilities) shown below; the rest are BIAN catalogue elements brought in with a domain.

**Against the real design:** 4 of 7 main elements match; 4 exist in both but differ; AID missed 1 real element.
- ≠ **POST /payment-instructions/{id}/execution** — the method differs — AID POST, real PUT.
- ≠ **GET /payment-instructions/{id}** — the method differs — AID GET, real POST.
- ≠ **Payment Instruction service (projected) — deployment (projected)** — the real component is deployed 2 times (ENV-PAY-PROD, ENV-PAY-UAT); AID projects one deployment and, by rule, no platform or environment.
- ≠ **Payment Instruction service (projected)** — the real design realises SD-PI with one component; the real one is split into 3 sub-components (Instruction Capture, Instruction Validation, Execution Gateway), AID projects one.
- ➖ **API-PI-06 GET /payment-instructions/{id}/events** — the real API implements no BIAN operation, so no rule could project it.

**Where AID stopped, and why:** SO-PI-06: Notify has no REST form — no API projected · SD-PE: no service operations in the A2 data — no component projected · SD-PA: no service operations in the A2 data — no component projected
