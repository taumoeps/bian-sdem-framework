# Workspace specification

> **Status: built (v0.17.0)** — how a workspace is started, filled, planned from and how its BIAN layer is chosen. Owner's decisions, 2026-10-30: one name, *workspace*; every workspace starts with the BIAN layer; architects narrow it per workspace. User view: [README — the commands in order](../../docs/sdem-workbench-user-guide.md#4c-from-your-designs-to-the-knowledge-graph--the-commands), the [onboarding workflow](../sdem-onboarding-workflow.md), [planning with AID](../sdem-planning-with-aid.md).

| Id | Requirement | Verified by |
|---|---|---|
| WS-01 | `sdem new --workspace DIR --person P` starts a workspace: all four layer datasets empty and `mappings.json` empty; the **BIAN catalogue** it chooses from is recorded, not copied — your organisation's shared layer (`bian/a2-service-domain.json`) when there is one, otherwise the base BIAN. `--bian FILE` starts with exactly that BIAN layer in A2; `--no-bian` with none. The workspace holds only the service domains its design needs: `sdem aid` brings them in (AID-W01), `sdem bian custom --add` adds one by hand. Checked before anything is written; a folder that exists and is not empty is refused; P is a person (CTL-21). *(Owner's decision, 2026-10-30: AID infers only the relevant domains.)* | tests |
| WS-02 | `workspace.json` records who started it and when, and its BIAN layer: source, release, selection (`all`, `custom`, `none`), number of service domains and, when custom, the domains chosen. | tests |
| WS-03 | `sdem load` loads only into a workspace started with `sdem new`; otherwise it refuses and gives the `sdem new` command. `--person` records who decided which suggestions became architecture data. | tests |
| WS-04 | `sdem bian custom --workspace DIR (--add …\|--only …\|--from FILE\|--all) --person P` changes one workspace's BIAN layer from the catalogue (or `--base FILE`): `--add` beside what it holds (inferred records keep their marks), the others exactly. Through the BIAN update (BU-*): checked, recorded in `bian-updates/`, never strands an approved connection; `workspace.json` records the domains held. `sdem bian update --root` refreshes in each workspace **only the domains it holds**, keeping their marks; a held domain the shared layer no longer has is kept and reported; nothing else is brought in. | tests |
| WS-05 | `sdem aid --workspace DIR --person P` fills the workspace's gaps in its own layer files, every inferred record marked (AID-W01…W07); `sdem aid confirm|reject` decide on them. File-based planning (`sdem aid project --workspace DIR`, into `DIR/plans/`, kept apart) still works. | tests |
| WS-06 | The option is `--workspace`; `sdem` still accepts the old `--estate`. Dashboards say *workspace*; `sdem home` writes `<out>/workspaces/<name>.html`. | tests |
| WS-07 | The catalogue `sdem aid` chooses from (the workspace's own A2 plus the BIAN catalogue, WS-01) holds each BIAN element once: a catalogue element the workspace already has under its own id — same type and natural key (LC-09), matched in rounds so a matched service domain's parts match too — is that record, and the catalogue's links point to it; where the workspace's record already has a link of that kind to that type, its own link wins. Before this, `sdem aid` refused five of the eight examples (2026-11-10) | `tests/test_migrate_change_sets.py` |
| WS-08 | **An organisation above its workspaces.** `sdem new --organisation NAME --person P` starts the folder `NAME`: `sdem-organisation.json` (name, who started it and when, its base profile), a starter base profile `profiles/NAME-base.json` that passes `sdem profile check` (empty types, attributes and rules, for the organisation to fill) and `workspaces/`. A person's decision. Refused: a folder that exists and is not empty, an organisation inside another, the workspace options (`--bian`, `--example`, `--from`, `--profile`, `--explore`) without `--workspace`. | `tests/test_organisation.py` |
| WS-09 | **A workspace in an organisation.** `sdem new --workspace DIR --organisation NAME --person P` starts the workspace inside the organisation: a relative `DIR` is from the organisation's folder, so it works from anywhere. `--organisation` is a folder, or the name of the organisation the current folder is in. Without it, the organisation is found by looking upward from the workspace's folder. Refused: a workspace outside the organisation's folder, and an organisation that does not exist (the error gives the command that starts it). The output and `--json` name the organisation and the profile chain. | `tests/test_organisation.py` |
| WS-10 | **The organisation's profile applies from the start.** The new workspace's own `sdem-profile.json` (`<organisation>-<workspace>`) extends the organisation's base profile and adds nothing yet — the workspace's own types, attributes and rules go there; it is checked before anything is written (PR-07). `workspace.json` records the organisation. An explicit `--profile FILE` (or a baseline's profile) wins over the organisation's. | `tests/test_organisation.py` |
